Design Patterns
Study Guide

A practical reference for the 22 GoF patterns you learned: what problem each solves, when to reach for it, and the code pressure that makes it useful.

How to study this page

Read the problem without the pattern first. Then expand the matching implementation. A pattern is valuable only when it removes a real pressure in the design—not because its name sounds sophisticated.

Cheat sheet: identify the core idea

Start with the problem you have, not a pattern name.

When you notice…Core ideaUse
Need to CREATE an object? Choose an implementation → Factory Create a matching family → Abstract Factory Many optional construction values → Builder Copy a configured base object → Prototype Exactly one shared instance → Singleton Need to CHANGE BEHAVIOUR? Replace an algorithm → Strategy Notify listeners → Observer Lifecycle determines actions → State Save/undo state → Memento Actions must queue/log/undo → Command Pass through checks → Chain of Responsibility Need to COMPOSE objects? Incompatible API → Adapter One item or a group → Composite Hide subsystem complexity → Facade Add stackable behaviour → Decorator Control access/lazy loading → Proxy Share repeated immutable data → Flyweight
Java examples are deliberately compact; production code should add domain validation and error handling where appropriate.
